# 应用筛选结构与包含语义设计

## 目标

梳理应用列表筛选的职责边界，减少 Sheet、状态模型和过滤策略之间的重复拼装与间接调用；同时明确并保持直觉一致的筛选契约：

- 应用类型条件之间使用 OR；
- 不同配置条件之间使用 OR；
- 应用名称和包名搜索使用包含匹配；
- 页面范围、配置应用判定和排序保持现有产品语义。

本次工作优先清理旧代码和旧入口，不保留新旧两套并行实现，不为了抽象而新增多层包装。

## 当前结构与问题

当前主要链路是：

```text
AppFilterSheet
  -> AppWorkspacePresentation.Actions.changeFilters
  -> MainHostWiringSession
  -> MainUiAction.FilterChanged
  -> MainUiState.withFilterState
  -> AppListVisibleSections.filter
  -> AppListFilter.matches
```

当前代码已经基本实现目标匹配关系，但表达不够清晰：

- `AppFilterSheet` 中重复拼接完整的 `withConfiguration(...)` 参数；
- `AppListFilterState` 用多个布尔字段和多个构造函数重载表达筛选集合，参数顺序容易误用；
- `AppListFilter` 同时处理搜索、页面范围、类型、配置条件；
- `AppListVisibleSections` 同时处理过滤和排序；
- `injectedOnly`、`fontConfiguredOnly` 等命名容易让人误解为精确匹配，而实际是正向条件匹配；
- Wear 页面存在旧式状态构造调用，需要收敛到同一筛选状态契约。

## 过滤契约

最终结果按以下关系计算：

```text
页面范围
AND 搜索条件
AND 类型条件组
AND 配置条件组
```

其中：

```text
类型条件组：选中的类型之间 OR
配置条件组：选中的配置条件之间 OR
```

具体规则：

- 选择用户应用和系统应用时，两类应用都保留；
- 选择已注入和字体配置时，应用满足任一条件即可保留；
- 搜索词只要出现在应用名称或包名中即可匹配，忽略大小写并去除首尾空格；
- “全部”表示对应条件组不施加限制；
- 配置应用页仍使用现有的用户可见配置判定，不改动 `configured` 的领域含义；
- 筛选完成后再按名称、更新时间或安装时间排序，并应用反向排序。

当前 `AppListFilter.matches` 的核心行为已经符合上述契约，因此实现阶段不应无理由改变结果集合；重点是让状态表达、入口命名和测试直接体现该契约。

## 结构设计

### 筛选 Sheet

`AppFilterSheet` 只负责渲染选项和发送语义明确的状态变更，不再手动复制完整布尔参数列表。重复的配置切换表达应收敛为一个状态方法，例如按
`ConfigurationFilter` 切换指定条件。

旧的未使用辅助 Composable 和不再需要的参数拼装代码一并删除，不保留兼容别名。

### 筛选状态

筛选状态继续作为单一不可变状态对象由 `MainUiState` 持有，但内部表达应明确区分：

- 选中的应用类型集合；
- 选中的配置条件集合；
- 排序方式；
- 是否反向排序。

如果为此实质修改现有 Java 状态类，应在同一变更中迁移到 Kotlin，并使用明确的 Java
可调用接口保持现有调用边界。旧的公开构造入口只在确有外部调用或恢复兼容需要时保留；其余旧重载和无调用入口应删除。

持久化 key 保持兼容。现有布尔 key 读取后转换为新的状态表达，保存时仍写入同一组
key，避免用户升级后筛选状态丢失。旧的迁移分支在确认没有使用者后删除，不能长期保留两套状态来源。

### 匹配策略

将匹配职责收敛到应用列表特性包内的单一策略入口：

- 搜索匹配：名称或包名包含；
- 页面匹配：已安装或用户可见配置；
- 类型匹配：选中类型集合内 OR；
- 配置匹配：任一选中配置条件满足即可；未选择配置条件表示不限制。

不新增 repository/use-case 层，也不把简单谓词拆成大量单方法类。只有在现有类职责无法保持清晰时，才将排序从过滤策略中提取为一个小型、无状态的排序函数或对象。

### 可见列表

`AppListVisibleSections` 保留为列表派生边界，但内部按“过滤后排序”的顺序调用明确的策略。`MainUiState`
继续作为唯一可见列表状态来源，Compose 不直接执行筛选、持久化或列表重建。

### Wear

Wear 使用同一个 `AppListFilterState` 和同一个匹配策略。删除 Wear 中旧的四参数状态构造方式；如果现有兼容入口仍被测试或外部
Java 调用使用，则先迁移调用方，再删除入口。

## 兼容性与潜在后果

- 已保存的筛选状态继续有效，不需要数据清理或重新选择；
- 已注入、禁用、视口、字体、字型和 Hook 条件的组合结果按包含语义使用 OR，不会要求多个能力同时存在；
- 类型多选仍会扩大到所选类型的并集；
- 配置条件多选会扩大到所选条件的并集；
- 空条件组继续表示不限制，具体类型取消到空集合的行为需在实现中固定并测试，不能由多个布尔值偶然决定；
- 批量选择使用未筛选全集的既有规则保持不变，筛选只影响展示，不丢失暂时隐藏的选择；
- 排序只改变顺序，不改变筛选结果。

## 测试与验收

补充或调整行为测试，至少覆盖：

- 用户类型和系统类型同时选择时的 OR 行为；
- 两个配置条件同时选择时的 OR 行为；
- 名称和包名的包含搜索；
- 搜索、类型、配置和页面条件的组合；
- 全部条件与空条件组；
- 三种排序和反向排序；
- 持久化读取旧 key、保存后恢复新状态；
- Wear 与手机/平板使用相同状态语义；
- 筛选后批量选择仍基于未筛选全集。

完成标准：

1. Sheet 中不再重复拼接同一组配置参数；
2. 过滤策略只有一个实际生效入口；
3. 旧的未使用构造函数、辅助方法和重复状态入口被删除；
4. 不新增无实际职责的包装层；
5. `:app:testAllDebugUnitTests` 通过；
6. Modern Debug 构建并安装到设备后验证筛选交互；
7. 最终 diff 不包含与筛选无关的结构或样式改动。
